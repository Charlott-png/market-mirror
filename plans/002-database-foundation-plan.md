## 1. Purpose

The approved MM-002 specification defines **what** the database foundation must do. This plan defines **how tests will prove it** and **how the minimum implementation will be organized**.

Nothing described as implementation is authorized until this plan is approved and the planned tests have been written, discovered, and observed in the expected Red state.

## 2. Planned technical approach

Market Mirror will use:

- **Flask-SQLAlchemy** to connect Flask and SQLAlchemy.
- **Flask-Migrate** to connect Flask and Alembic migrations.
- **SQLite** files for local development and isolated tests.
- A configurable database URL for future PostgreSQL deployment.
- `Decimal`/SQL `Numeric` for prices.
- UTC timestamps generated by trusted application behaviour.
- SQL constraints plus Python model validation.

The application will keep using the application factory introduced in MM-001. Database extension objects will be created once without binding to an app, then initialized inside `create_app()`.

This pattern is similar to owning one reusable power adapter rather than permanently wiring an appliance into one room. Development and pytest can connect the same database tools to different application configurations.

## 5. Configuration plan

### IMP-DB-001: Configuration classes

Planned file: `config.py`.

Responsibilities:

- Define a safe common base configuration.
- Use an SQLite file under `instance/` for development when no database URL is provided.
- Accept a database URL from an environment variable for future production use.
- Disable SQLAlchemy's modification-tracking overhead.
- Allow tests to override the database URL with a temporary path.
- Avoid hard-coded production secrets.

The application factory will continue accepting a mapping such as `{"TESTING": True}` so MM-001 tests remain compatible.

Mapped requirements: DB-002, DB-003, DB-004, NFR-DB-002, NFR-DB-003.

### IMP-DB-002: Extension initialization

Planned file: `app/extensions.py` and changes to `app/__init__.py`.

Responsibilities:

- Create unbound `db` and `migrate` objects.
- Load configuration before extension initialization.
- Initialize both objects inside `create_app()`.
- Import models at the correct time so migration discovery sees them.
- Register CLI commands.
- Enable SQLite foreign-key enforcement on connections.
- Preserve existing blueprint and 404 registration.

Mapped requirements: DB-001 through DB-004, STRUCT-001, STRUCT-003.

## 6. User model plan

### IMP-USER-001: User columns

Planned file: `app/models/user.py`.

The model will define all MM-002 user fields and database rules.

Implementation decisions:

- Store usernames in normalized lowercase form. This makes case-insensitive uniqueness consistent across SQLite and PostgreSQL without database-specific collation tricks.
- Store email in lowercase after trimming.
- Use named unique constraints for username and email.
- Use model validators for username format, field lengths, and normalization.
- Use non-null UTC `created_at` and `updated_at` defaults.
- Use a safe `__repr__` containing only ID and username.
- Define a one-to-many `products` relationship.
- Do not implement password setting/checking methods until MM-003; MM-002 only stores a supplied secure hash.

An attempted direct assignment such as `" Alice "` will normalize to `"alice"`. Invalid format or length will raise a clear Python validation exception before commit. The database unique constraint remains the second line of defence.

Mapped requirements: USER-001 through USER-003, TIME-001, TIME-002, VAL-001, NFR-DB-001.

### IMP-USER-002: Restrictive deletion

The relationship will not use an automatic delete cascade from user to product. SQLite foreign keys will be enabled so a database-level user deletion with owned products is rejected.

Mapped requirements: REL-002, W02-DELETE-003.

## 7. Product model plan

### IMP-PRODUCT-001: Product columns and constants

Planned file: `app/models/product.py`.

Responsibilities:

- Define one authoritative mapping for category, condition, and status keys/labels.
- Define `USD` as the only currency.
- Store price as `Numeric(10, 2)` and use `Decimal` in Python.
- Add check constraints for price range and approved choice keys.
- Add an index on `seller_id`.
- Add initial indexes useful for future public queries: status, category, and created time only when the generated migration is reviewed and their purpose is documented.
- Validate and trim title/description.
- Keep `image_filename` nullable and unused in MM-002.
- Use a safe shortened-title `__repr__`.
- Define the `seller` relationship back to User.

The implementation will not create product forms or routes.

Mapped requirements: PRODUCT-001 through PRODUCT-004, MONEY-001, MONEY-002, VAL-001, NFR-DB-005.

### IMP-PRODUCT-002: Timestamp handling

Use timezone-aware UTC values from a small callable rather than evaluating a timestamp once during module import. `updated_at` will use an update callback. Tests will compare UTC meaning rather than assuming the host's local timezone.

Mapped requirements: TIME-001 and TIME-002.

## 8. Transaction and validation plan

### IMP-DATA-001: Validation layers

Python model validators will provide early, understandable exceptions for:

- Username format/length.
- Email normalization and maximum length.
- Bio maximum length.
- Product title and description boundaries.
- Decimal conversion and price range.
- Currency, category, condition, and status choices.
- Image-filename maximum length if assigned internally.

Database constraints will independently protect:

- Required non-null fields.
- Unique normalized identity fields.
- Valid foreign key.
- Price range.
- Approved currency/category/condition/status values.

Mapped requirements: VAL-001, W02-SCHEMA-001, W02-PRICE-002.

### IMP-DATA-002: Rollback discipline

The seed command and tests that intentionally trigger an integrity error will roll back the database session before reusing it. Future web services will follow the same rule.

Mapped requirements: VAL-002, NFR-DB-004, X-DATA-001.

## 9. Migration plan

### IMP-MIG-001: Initialize migration history

After Red tests exist, Implementation will initialize Flask-Migrate and generate an initial revision from the models.

The generated revision must be manually inspected for:

- Both table names.
- Every approved column and type.
- Named unique and check constraints.
- Foreign key from `products.seller_id` to `users.id`.
- Indexes and their names.
- Creation order: users before products.
- Downgrade order: products before users.

The generated migration may be edited through `apply_patch` when Alembic misses or names a required constraint incorrectly.

Mapped requirements: MIG-001 through MIG-004.

### IMP-MIG-002: Migration execution tests

Migration tests will use a temporary SQLite file and Alembic/Flask CLI rather than the development database.

They will prove:

- Empty → latest creates schema.
- Running upgrade again is safe.
- Latest → base removes schema in dependency order.
- Base → latest recreates the expected schema.

Migration tests will not claim that downgrading preserves table data; downgrading a table-creation migration removes those disposable tables.

## 10. Seed command plan

### IMP-SEED-001: Command design

Planned file: `app/commands.py`.

The command will:

- Be registered explicitly with Flask's CLI.
- Use fixed fictional seed identifiers and normalized values.
- Create at least 3 users and 12 varied products.
- Store generated secure password hashes, but never print the plain seed password or hash.
- Use `Decimal` price values.
- Include active, sold, and archived products.
- Commit in one transaction.
- Roll back and return a non-zero failure if any seed operation fails.
- Refuse or safely skip existing seed identities/products so the second run creates no duplicates.
- Never delete non-seed data.
- Refuse destructive reset behaviour because MM-002 contains no reset command.

Mapped requirements: SEED-001 through SEED-004, W02-SEED-005.

### IMP-SEED-002: Seed identity strategy

Seed users will use recognizable fictional emails such as the `example.test` reserved domain. Seed products will use stable titles plus seller/category data for lookup. The exact dataset belongs in code only after tests define the expected counts and variety.

The command will report counts such as created versus already present without outputting private fields.

## 12. Test-fixture design

### TEST-FIX-001: Temporary application database

`tests/conftest.py` will keep the existing `app` and `client` fixture names so MM-001 tests do not change.

The `app` fixture will additionally:

1. Receive pytest's `tmp_path`.
2. Create a unique SQLite database URL inside that directory.
3. Pass `TESTING=True` and the temporary URL to `create_app()`.
4. Create tables for model/route tests inside an application context.
5. Yield the application.
6. Roll back/remove the session and drop tables after the test.

Migration tests will use a separate fixture and will not call `create_all()`, because they must prove migrations create the schema.

### TEST-FIX-002: Factories

Small helper fixtures/functions will create:

- Valid unique users with already-hashed placeholder passwords.
- Valid products using `Decimal` and an explicit seller.
- A second independent user for relationship and uniqueness tests.

Factories will allow field overrides so boundary tests remain short and readable.

### User model

#### TEST-USER-001: Valid user persists

- Create a valid user and commit.
- Clear/remove the session and query again.
- Assert normalized username/email and timestamps persist.

Requirements: User field table, USER-001, AC-DB-002.

#### TEST-USER-002: Username and email normalize

- Assign surrounding whitespace and uppercase letters.
- Assert stored username/email use approved lowercase normalized form.

Requirements: USER-001.

#### TEST-USER-003: Invalid user field boundaries are rejected

Parameterize:

- Username lengths 2, 3, 30, and 31.
- Invalid spaces/symbols versus allowed underscore/hyphen.
- Empty and overlong email/password hash.
- Bio at 500 and 501 characters.

Assert exact boundaries and no invalid committed row.

Requirements: User field table, VAL-001.

#### TEST-USER-004: Duplicate normalized identity is rejected

- Commit one user.
- Attempt case/whitespace-equivalent username and email combinations.
- Expect a validation or integrity failure according to layer.
- Roll back and confirm the original is unchanged and the session works.

Requirements: USER-001, AC-DB-004.

#### TEST-USER-005: Representation hides secrets

- Create a user with recognizable email/hash canaries.
- Call `repr(user)`.
- Assert ID/username may appear but email/hash do not.

Requirements: USER-002, USER-003, X-PRIV-001.

### Product model and relationships

#### TEST-PRODUCT-001: Valid products persist through both relationship directions

- Create one user and two valid products.
- Commit and begin a fresh session query.
- Assert `user.products` returns exactly both.
- Assert each `product.seller` is the user.

Requirements: REL-001, AC-DB-002.

#### TEST-PRODUCT-002: Missing or nonexistent seller is rejected

#### TEST-PRODUCT-003: Price round trip is exact

Requirements: MONEY-002, AC-DB-005.

#### TEST-PRODUCT-004: Invalid price boundaries are rejected

#### TEST-PRODUCT-005: Choice fields enforce allow lists

#### TEST-PRODUCT-006: Text boundaries are enforced

#### TEST-PRODUCT-007: Product representation is safe

Requirements: PRODUCT-004, X-PRIV-001.

#### TEST-PRODUCT-008: Timestamps behave correctly

- Freeze or compare controlled UTC times.

## 16. Expected Red stage

After plan approval, only test files and necessary test-fixture changes will be created.

Validation steps:

1. Check Python syntax for all test files.
2. Run pytest collection and record the number of discovered tests.
3. Run the suite.
4. Expect existing MM-001 tests to remain Green where they do not require the changed fixture.
5. Expect new MM-002 tests to fail because database extensions, configuration, models, migrations, dependency declarations, and seed commands do not exist.

Tests shall import future database modules inside fixtures/test functions where practical so pytest can collect the full intended suite. A meaningful assertion/import failure is acceptable Red evidence; invalid test syntax is not.

The Testing stage may expose that a test expectation is ambiguous or impossible. In that case, revise this plan/specification before implementation rather than silently weakening the test.

## 18. Definition of done

MM-002 will be complete only when:

- All approved fields, constraints, choices, and relationships exist.
- SQLite foreign keys are proven enabled.
- Price exactness and boundaries are proven.
- Timestamps follow the approved UTC behaviour.
- User deletion with products is restricted.
- A clean database upgrades from migrations.
- Downgrade/re-upgrade works on disposable data.
- Seed data is fictional, varied, repeatable, and non-destructive.
- Tests cannot touch development data.
- All new tests and the original nine MM-001 tests pass.
- README database instructions work from a clean setup.
- No database, `.venv`, cache, or secret is tracked by Git.
- The student can explain each database concept in their own words.

It does not authorize database implementation until the test files have valid syntax, pytest discovers them, and their expected Red failures are recorded.
