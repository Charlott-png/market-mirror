# MM-025 — Functional checkout, orders, and sold listings

Status: IMPLEMENTED AND VERIFIED — approved 2026-11-06; completed 2026-11-07 (Asia/Shanghai)

Date: 2026-11-06 (Asia/Shanghai)

## 1. Purpose

Replace MM-019's non-mutating checkout demonstration with a complete local
marketplace checkout. When a signed-in buyer confirms Checkout, Market Mirror
will create a permanent order, record which listings were purchased, change
those listings from `active` to `sold`, remove the purchased rows from that
buyer's cart, and redirect to a success page headed **Thank you for your
purchase**.

This is a functional **class-project purchase record**, not a real-money payment
system. It does not charge a card, transfer money, calculate shipping or promise
delivery. The interface must say this clearly so a user is never misled.

## 2. Relationship to earlier features

MM-025 changes only the Checkout behavior approved in MM-019:

- MM-019 Add to Cart, Remove from Cart, private account ownership, navigation
  count, pagination, current-price subtotal, unavailable placeholders and
  Saved-product separation remain in force.
- The old message saying that no order is created is removed.
- A successful Checkout now performs the database changes defined here.
- Existing product, seller-profile, search, recommendation, messaging, mobile,
  image and AI behavior remains unchanged unless this specification explicitly
  names an integration point.

An order does not create a message or notification, and checking out a product
does not remove it from anyone's Saved products.

## 3. User story

> As a signed-in buyer, I want Checkout to record my purchase, mark the
> listings sold, clear the purchased items from my cart, and show a permanent
> confirmation page, so the marketplace demonstrates a complete transaction.

## 4. Meaning of a successful checkout

A checkout succeeds only when every cart row is still eligible at the instant
the transaction is committed. An eligible row has:

- an existing product;
- `product.status == "active"`;
- an enabled seller;
- a seller different from the signed-in buyer; and
- the same product version and current price that were shown when the checkout
  form was rendered.

Success is **all or nothing**. Market Mirror must never create an order for only
some of the cart while silently leaving the rest behind.

After a successful commit:

1. exactly one `Order` belongs to the signed-in buyer;
2. it contains one `OrderItem` snapshot for every purchased cart row;
3. every purchased `Product.status` is stored as lowercase `sold` and displayed
   to people as **Sold**;
4. the buyer's purchased cart rows are deleted;
5. the navigation cart count reflects the remaining rows, normally zero; and
6. the browser receives a `303 See Other` redirect to that order's success
   page.

At the instant of a successful commit, the checkout set is empty in the
buyer's cart. If another browser tab adds a different item after that commit,
that later action may correctly create a new cart row.

## 5. Order data model

### 5.1 `orders` table

Add an `Order` model and migration with:

| Field | Requirement |
| --- | --- |
| `id` | Integer primary key generated by the database. |
| `buyer_id` | Required foreign key to `users.id` using the project's restrictive deletion policy; indexed. |
| `status` | Required string; MM-025 allows only `completed`. |
| `total_amount` | Required exact Money/Decimal value; never a binary float. |
| `currency` | Required `USD`. |
| `checkout_nonce` | Required unpredictable identifier used to make repeated submissions safe. |
| `created_at` | Required timezone-aware UTC timestamp. |

The database must enforce a unique `(buyer_id, checkout_nonce)` pair. A nonce
cannot accidentally produce two orders for one buyer. The database must also
enforce the allowed status, currency and positive Money range using constraints
compatible with the project's SQLite development database and PostgreSQL
deployment design.

### 5.2 `order_items` table

An order header alone cannot explain what was purchased. Add an `OrderItem`
model and migration with:

| Field | Requirement |
| --- | --- |
| `id` | Integer primary key generated by the database. |
| `order_id` | Required foreign key to `orders.id`; indexed. |
| `product_id` | Required foreign key to `products.id`; unique across all order items. |
| `seller_id` | Required foreign key to the seller's `users.id`; indexed. |
| `product_title` | Required snapshot of the title at checkout, 3–120 characters. |
| `seller_username` | Required snapshot of the public seller username at checkout. |
| `unit_price` | Required exact Money/Decimal snapshot at checkout. |
| `currency` | Required `USD`. |

`product_id` is globally unique in `order_items` because one Market Mirror
listing represents one physical marketplace item and may be sold only once.
This database rule is a final safety net when two buyers check out at almost the
same moment.

The snapshots preserve a truthful receipt even if ordinary profile or product
presentation changes later. Descriptions, images, email addresses and private
account fields are not copied into an order.

The order total must equal the exact sum of its order-item prices when the
transaction is created. The service layer guarantees that an order has at least
one item because a relational database cannot express that cross-table rule as
a simple column constraint.

### 5.3 Relationships and retention

- An order belongs to one buyer and has one or more ordered items.
- An ordered item refers to one product and its seller.
- MM-025 provides no web action for editing or deleting an order or order item.
- Existing restrictive foreign keys prevent a referenced buyer, seller or
  product from being silently deleted and destroying purchase history.
- The migration must upgrade a fresh database and the existing project
  database without modifying old users, products, carts or saved products.
- Its downgrade removes only the MM-025 order tables and indexes. Downgrading a
  real database is data-destructive and will not be run against the student's
  demo database as part of normal verification.

## 6. Checkout form and stale-cart protection

The server renders one Checkout form for the complete cart, even when the cart
items are spread across several display pages. In addition to the existing CSRF
field, the form contains a server-signed checkout token.

The signed token contains only constant-size safety data:

- the current buyer ID;
- a cryptographically random nonce;
- a hash/fingerprint of the complete eligible cart; and
- a signed creation time.

The fingerprint is produced from a canonical, deterministic list containing
each cart product ID, product version, exact price and currency. The raw list is
not trusted from the browser. On POST, the server reloads the full cart and
recomputes the fingerprint.

This protects the buyer from a price, status or cart change between viewing the
summary and clicking Checkout. It also keeps the hidden field small for large
carts. The token is bound to the signed-in buyer, must have a valid server
signature and expires after 30 minutes.

- A missing, malformed, forged, or wrong-user token returns HTTP 400 with no
  database changes.
- An expired token or a valid token whose cart fingerprint is stale returns
  HTTP 409, shows the refreshed cart, and asks the buyer to review it again.
- Browser-supplied product IDs, prices, totals, seller IDs, statuses, buyer IDs
  or order IDs must never decide the purchase.

## 7. Checkout transaction

`POST /cart/checkout` remains authenticated and CSRF-protected. It performs the
following work inside one database transaction:

1. Verify and decode the signed checkout token.
2. If an order already exists for the current buyer and nonce, redirect to that
   existing success page without creating or changing anything.
3. Reload the current buyer's full cart and the referenced product/seller rows
   from the database using appropriate write/concurrency protection.
4. Reject an empty, changed or ineligible cart before creating an order.
5. Recompute the cart fingerprint and exact Decimal total.
6. Create one completed `Order` using the server-derived buyer, total and nonce.
7. Create one `OrderItem` snapshot per product.
8. Change each purchased product from `active` to `sold`. Product optimistic
   versions continue to protect against competing edits.
9. Delete the purchased `CartItem` rows belonging to this buyer.
10. Commit all changes once.

SQL locking differs between SQLite and PostgreSQL, so the implementation plan
must choose and test a correct strategy for both. Regardless of technique, the
observable rule is identical: no product can be ordered twice and no partial
checkout state may remain.

If any insert, update, delete, constraint check or commit fails, the whole
transaction is rolled back. There must be:

- no incomplete or empty order;
- no partial set of order items;
- no product left sold by the failed attempt; and
- no cart row lost by the failed attempt.

The user sees a safe generic error. Database details, SQL, file paths and
private values must not appear in the response.

## 8. Validation and conflict behavior

### 8.1 Empty cart

A direct checkout request with an empty cart creates no order and returns a
helpful HTTP 400 cart response. It must not display a purchase-success message.

### 8.2 Unavailable or changed cart

If one or more rows are sold, archived, missing, offered by a disabled seller,
newly owned by the buyer, differently priced, differently versioned, added or
removed, Checkout returns HTTP 409 and performs no purchase mutation.

Unavailable rows keep MM-019's privacy-preserving **Unavailable product**
presentation. The page must not reveal private details about an archived or
otherwise inaccessible listing.

### 8.3 Competing buyers

Several users may place the same active listing in their carts because a cart
is not a reservation. If they submit checkout concurrently:

- at most one committed order may contain that product;
- exactly that winning checkout marks it sold;
- each losing checkout returns a safe conflict result and creates no order;
- a losing multi-item checkout remains entirely uncommitted; and
- the losing buyer's cart rows remain for review/removal.

### 8.4 Other users' carts

When one buyer purchases a product, a row for that product may remain in a
different buyer's cart. This preserves MM-019's rule that a GET request does not
silently mutate cart data. The other buyer sees the generic unavailable row and
must remove it; their count continues to include it until removal.

### 8.5 Repeated submissions

Double-clicking Checkout, refreshing after a slow response, or retrying the
same valid token must not create duplicate orders. The `(buyer_id,
checkout_nonce)` constraint and existing-order lookup make the request
idempotent: the buyer is redirected to the one existing success page.

A retry cannot purchase a new cart using an old token because its cart
fingerprint and recorded nonce no longer represent a new checkout.

## 9. Success page

Add authenticated `GET /orders/<int:order_id>/success`.

Only the order's buyer may view it. An anonymous visitor is sent to login using
the existing safe local return behavior. A different signed-in user receives
HTTP 404 so the page does not reveal whether another person's order exists.

The page returns HTTP 200 and contains:

- exactly one H1: **Thank you for your purchase**;
- a visible order number;
- completed date/time presented consistently with the project;
- each purchased product-title snapshot;
- each seller-username snapshot;
- each exact item price and `USD` currency;
- the exact order total;
- a clear note that this was a Market Mirror classroom/demo purchase and no
  real payment was collected;
- a link to continue exploring products; and
- navigation whose cart count reflects the completed checkout.

The page must work without JavaScript, be keyboard accessible, wrap on narrow
screens, use existing focus styles, and remain understandable at browser zoom.
Refreshing this GET page is read-only and cannot create another order or alter
the cart/products.

Do not show buyer email, seller email, password data, provider keys, private
messages or full product descriptions on this page.

## 10. Cart-page changes

- Replace the old “no order will be created” wording with an accurate note:
  Checkout records a classroom purchase and marks each item sold, but does not
  take real payment.
- The enabled Checkout form includes CSRF and the signed token.
- Checkout stays disabled when the cart is empty or contains an unavailable
  row.
- The shown total is still the current exact full-cart total, not merely the
  current pagination page.
- After success, visiting `/cart` shows the normal empty state unless a later
  action has added a new item.

## 11. Product and seller integration

- A purchased product uses the existing `sold` status; no new spelling or
  second sold flag is introduced.
- Sold products stop appearing as active products in public browse, live search
  and recommendation results under existing status filters.
- The seller's listing-management view displays the existing Sold label.
- Public cards can no longer add that product to a cart.
- Existing product ownership, image and message records are not deleted.
- A purchase does not automatically archive the listing or disable the seller.

## 12. Security and privacy requirements

- Authentication is required for checkout and order success pages.
- CSRF protection is required on Checkout; GET requests never purchase.
- Every cart/order query is scoped from `current_user`, never a submitted
  `user_id`.
- The server independently derives products, sellers, prices, currency, total
  and status from current database records.
- Signed checkout tokens use the application's secret and an MM-025-specific
  salt; they do not replace CSRF protection.
- Nonces are generated with a cryptographically secure random generator and are
  not predictable sequence numbers.
- Order ownership failures use 404 to reduce information leakage.
- User-controlled snapshot text is auto-escaped in HTML.
- No payment, API, email or AI service is called during checkout.
- Normal application rate limiting and safe error handling remain active.
- Logs may record an order ID and generic outcome but not secret tokens,
  passwords, CSRF values or unnecessary private account data.

## 15. Out of scope

MM-025 intentionally does not include:

- credit/debit cards, Stripe, PayPal, bank transfers or real payment capture;
- shipping addresses, delivery tracking, taxes, fees, discounts or coupons;
- quantities or inventory counts (one listing is one item);
- guest checkout or anonymous carts;
- seller payouts, commissions, refunds, cancellations or returns;
- order editing/deletion;
- a complete order-history index page;
- receipts by email, seller notifications or automatic messages;
- multi-currency conversion; or
- changing old order data when a current product/profile changes.

Each item needs its own future specification because it introduces separate
security, legal, financial or user-experience rules.

## 16. Concepts to understand

### A database transaction is an all-or-nothing box

Imagine Checkout has four chores: write the receipt, mark products sold, erase
the cart rows and save everything. A transaction means the database completes
all four chores together or pretends none happened. This prevents a scary state
such as “the cart is empty, but no order exists.”

### An order header and its items have different jobs

The `orders` row says **who bought, when, and the total**. The `order_items` rows
say **which products and at what prices**. This one-to-many relationship is like
one paper receipt with several printed lines.

### A snapshot preserves history

The current product record may change later. Copying the title, public seller
name and price into `order_items` records what was true at checkout. It is not
the same as copying every product field; only receipt information is preserved.

### Idempotency makes retries safe

Web browsers can send the same request twice because of a double-click or a
slow network. The random nonce acts like a submission serial number. If Market
Mirror has already processed that serial number for the buyer, it shows the
same order instead of creating another.

### Concurrency means requests can overlap

Two buyers can click Checkout almost simultaneously. Application checks,
product versioning, transaction protection and the unique ordered-product rule
work together so only one can successfully purchase a one-of-a-kind listing.

### A signed token is a tamper-evident seal

The browser must send some form data back, but users can edit browser data. A
server signature is like a seal: the server can detect alteration. The cart
fingerprint also detects legitimate changes, such as a seller changing the
price, and asks the buyer to review the new summary.
