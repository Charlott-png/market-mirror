# MM-026 — Up to five product images and thumbnail gallery

Status: IMPLEMENTED — MM-026 approved 2026-11-07; PLAN-026 approved 2026-11-07

Date: 2026-11-07 (Asia/Shanghai)

## 1. Purpose

Allow a seller to publish as many as five photos for one product so buyers can
inspect different angles. Upgrade the Sell/Edit image controls to accept a
small ordered set of pictures, and add an accessible thumbnail gallery to the
product-detail page. Selecting a thumbnail changes the large displayed picture;
the existing hover zoom and lightbox then use that selected picture.

Images remain optional. A listing may contain zero, one, two, three, four or
five photos.

## 2. Relationship to existing Market Mirror features

MM-026 extends, rather than replaces:

- MM-002 product storage and ownership;
- MM-017 hover zoom and lightbox;
- MM-019 cart cards and product cover images;
- MM-022 drag-and-drop selection and local previews;
- MM-023/MM-024 AI Vision title/category suggestions; and
- MM-025 completed orders and historical receipt snapshots.

The first photo is the **cover photo**. Existing catalogue, seller, Saved,
cart, dashboard and recommendation cards continue showing only this cover, so
cards do not become crowded or download five large files.

Checkout and order items do not copy product pictures. An order remains a
title/seller/price snapshot and does not gain image ownership or deletion
rules.

## 3. User stories

> As a seller, I want to choose up to five product photos before saving, so I
> can show the front, back, sides and important details.

> As a buyer, I want to select small thumbnails on the product page, so I can
> inspect every available angle without repeatedly leaving or reloading it.

## 4. Image limits and authoritative server validation

Every selected image must independently satisfy the current server rules:

- JPEG or PNG input bytes;
- nonempty;
- no larger than 5 MiB;
- one frame only (no animated image);
- no more than 12 million source pixels;
- valid, readable image bytes;
- EXIF orientation applied;
- resized to fit within 1600 × 1600;
- converted to a newly encoded JPEG; and
- original metadata removed.

Additional MM-026 limits are:

- at most five files;
- at most 25 MiB of raw selected image bytes in total; and
- a bounded multipart request of 26 MiB, leaving space for normal form fields
  and multipart headers.

The browser's `accept`, MIME type, filename and thumbnail preview remain hints,
not proof. Pillow-based server validation is authoritative for every file.

If any file in a submitted group is invalid, the whole listing-image operation
fails. The application must not silently save only the acceptable pictures.

## 5. Database design and backward compatibility

### 5.1 New `product_images` table

Add a `ProductImage` model and migration:

| Field | Requirement |
| --- | --- |
| `id` | Integer primary key generated by the database. |
| `product_id` | Required foreign key to `products.id`; indexed; child rows are removed only when their product is intentionally removed. |
| `filename` | Required UUID-style normalized JPEG filename, maximum 255 characters, globally unique. |
| `position` | Required integer from 0 through 4. Position 0 is the cover. |
| `created_at` | Required timezone-aware UTC timestamp. |

The database must enforce:

- unique `(product_id, position)`;
- unique `filename`;
- `position BETWEEN 0 AND 4`;
- bounded nonblank filename text; and
- valid parent foreign keys.

The application guarantees positions are contiguous (`0, 1, 2...`) and that a
product has at most five rows. The position check and unique pair provide the
database-level maximum; service tests enforce no gaps.

### 5.2 Cover compatibility

The existing `products.image_filename` column remains as the product's cover
pointer. Removing it now would require rebuilding a heavily referenced SQLite
parent table and would break existing card code, fixtures and generated demo
assets.

For listings saved by MM-026:

- `product_images.position == 0` is the gallery's authoritative cover row; and
- `products.image_filename` stores the same filename as a compatibility/cache
  pointer used by existing cards.

All application writes must update these two values together in one database
transaction. Maintenance tests detect drift. A legacy/test product with only
`image_filename` and no gallery rows continues to behave as a one-image
product, so old data and existing factories remain readable.

### 5.3 Migration backfill

The migration creates `product_images`, then inserts a position-0 row for every
existing product whose `image_filename` is not null. It does not copy, rename,
re-encode or delete image files.

Backfill must preserve product IDs, statuses, versions, timestamps, carts,
orders and all other data. It must be safe on products whose referenced file is
currently missing; file reconciliation reports that problem separately.

Downgrading removes only `product_images`. Because
`products.image_filename` remains populated, the cover picture still works
after an isolated downgrade. The real demo database will be backed up before a
forward migration and will not be downgraded during normal verification.

## 6. Sell a Product upload behavior

The authenticated `/listings/new` form upgrades its existing image input to a
multiple file input while keeping the field name `image` for compatibility.

The upload zone must say, in beginner-friendly language:

- drag up to five photos here or use the file chooser;
- JPEG or PNG only;
- maximum 5 MiB per photo and 25 MiB total; and
- the first photo becomes the cover shown on cards.

The native input includes `multiple` and
`accept="image/jpeg,image/png"`. With JavaScript disabled, the ordinary native
control can still select multiple files and submit them normally.

The seller may save with no images. Selecting images never automatically saves
or uploads the listing.

## 7. Drag/drop and local preview gallery

MM-022's highlighted drag zone remains, but its single-preview behavior becomes
an ordered preview list.

### 7.1 Selection rules

- One picker action or one drop may supply one through five files.
- A new picker/drop selection replaces the current unsaved selection rather
  than creating an unpredictable mixture of old and new files.
- More than five files rejects the complete selection with a clear message.
- If any selected file is empty, over 5 MiB, unsupported or the combined size
  is above 25 MiB, reject and clear the complete selection.
- Dropped directories and non-file payloads remain rejected.
- The client does not silently truncate to five or select only the first valid
  file.

### 7.2 Previews

For a preliminarily acceptable group:

- create one object URL per file;
- show up to five small thumbnails in file-selection order;
- show each filename as plain text, safely wrapping long/Unicode names;
- label the first thumbnail **Cover photo**;
- give each preview useful alternative text such as `Selected photo 2 preview`;
- announce `3 photos selected` (with correct singular/plural) in the polite
  status region; and
- place all files into the real multiple input before form submission.

There is no drag-to-reorder interface in MM-026. To change the order, the
seller chooses the files again in the desired order. This keeps the feature
small enough to understand and demonstrate.

If any browser preview cannot decode, clear the entire group, revoke every
object URL and ask the seller to choose readable JPEG/PNG files. Replacing,
rejecting or leaving the page revokes all old object URLs.

The page uses `textContent`, DOM properties and escaped Jinja values; it never
inserts a filename through `innerHTML`.

## 8. AI Vision behavior

AI Vision continues suggesting only one Title and Category, not descriptions
or per-photo labels.

- When several images are selected, only the first/cover file is sent to the
  configured vision provider.
- The disclosure and status text must say that the cover photo is analyzed.
- The other selected images remain browser-local until Save Listing and are
  never sent to Gemini/OpenAI.
- Changing the selection cancels an older analysis and analyzes the new first
  file under the existing race/dirty-field protections.
- Turning AI off, provider failure or no API key leaves all manual and
  multi-image upload behavior usable.
- Text category/price suggestion requests continue deleting all `image` parts
  from their `FormData`.

AI output never changes image order, removes an image, saves a listing or
chooses a cover.

## 9. New-listing transaction and file cleanup

On a valid Save Listing submission:

1. Validate form text and require zero through five upload objects.
2. Normalize/store each file in selection order using a fresh unpredictable
   `.jpg` filename.
3. If any normalization/storage step fails, remove every file newly stored by
   this request and create no product/gallery rows.
4. Create the `Product` and flush to obtain its ID.
5. Add one `ProductImage` row per stored file with positions `0...n-1`.
6. Set `Product.image_filename` to position 0, or `None` for no photos.
7. Add the existing replay-protection `ListingSubmission` row.
8. Commit once.

If the database flush/commit fails, rollback all rows and remove all newly
stored files. A replay with the same listing request token redirects to the one
existing product and cannot create duplicate pictures.

## 10. Edit Listing behavior

The owner-only Edit Listing page will show the current ordered gallery and a
multiple-image control.

- Leaving the image input empty keeps every current image unchanged.
- Selecting one through five new images means **replace the entire gallery**
  after Save. The page states this before selection.
- The newly selected first image becomes the new cover.
- There is no separate delete-one-image or reorder-current-gallery action in
  MM-026.
- The seller can intentionally create an image-free listing only when a future
  separately specified remove-all control is added; selecting an empty input in
  this feature means “keep current gallery,” preserving existing behavior.

Replacement is compensated safely:

1. store/validate every new file;
2. update ProductImage rows and the cover pointer inside the optimistic-version
   product transaction;
3. commit once;
4. only after a successful commit, discard old files no longer referenced; and
5. on validation, stale-version or database failure, discard new files and keep
   the complete old gallery.

Replacing the gallery cannot leave a mixture of old and new photos.

AI Vision remains available only on **Sell a Product**, matching MM-023/MM-024;
Edit does not send replacement photos to a provider.

## 11. Product-detail thumbnail gallery

Public active/sold detail pages and the owner's archived preview use the same
gallery component.

### 11.1 Initial rendering

- Load ProductImage rows ordered by `position`, using the legacy cover fallback
  only when no rows exist.
- Ignore a missing file when building the usable on-page gallery and let the
  maintenance command report it.
- If at least one usable image exists, display the first usable image as the
  large main photo.
- If every reference is missing or there are no references, show the existing
  noninteractive **No photo yet** placeholder.
- With exactly one usable image, keep the existing main-image/lightbox layout
  and do not show a pointless one-item thumbnail strip.

### 11.2 Thumbnail strip

With two through five usable images:

- show one small thumbnail per image below the main photo;
- preserve image proportions without stretching;
- wrap or horizontally scroll inside the gallery on narrow screens without
  causing whole-page overflow;
- identify the selected thumbnail with more than color alone, such as a border
  plus `aria-current="true"`;
- give controls accessible names such as `Show photo 2 of 4 for Laptop`; and
- lazy-load non-cover thumbnails where browser behavior permits.

### 11.3 Switching images

Clicking/tapping or keyboard-activating a thumbnail:

- changes the large photo without a page reload;
- updates the selected state and a polite `Showing photo 2 of 4` message;
- updates the main image alternative text to include its position;
- updates the main image's ordinary fallback link; and
- makes the existing lightbox open the newly selected image.

Focus remains on the selected thumbnail. Switching images performs no database
write, analytics event or network call other than the ordinary same-origin
image request.

### 11.4 No-JavaScript fallback

Each thumbnail is an ordinary link to its authorized media URL. Without
JavaScript, the cover remains the main image and selecting another thumbnail
opens that image directly. The controls must not become dead buttons.

## 12. Lightbox integration

MM-017 behavior remains in force:

- hover zoom applies to whichever main image is selected;
- the full-screen overlay opens the selected image;
- Close, Escape and backdrop click work;
- focus and scroll restoration remain correct;
- reduced-motion behavior remains respected; and
- a failed selected image produces the existing readable error while retaining
  a usable Close button.

MM-026 does not add Previous/Next buttons inside the lightbox. A user closes it,
chooses a different thumbnail, and opens it again. Lightbox slideshow controls
can be specified separately if later desired.

## 13. Media authorization

`GET /media/products/<filename>` must authorize both cover and gallery files.

- A filename is served only when referenced by either the product's legacy
  cover pointer or one of that product's ProductImage rows.
- Active and sold product media retain their current public behavior.
- Archived product media remains visible only to its authenticated owner.
- An unreferenced/orphan filename, missing file, invalid filename, other
  seller's private archived image or path-manipulation attempt returns 404.
- The route never accepts a client-supplied product/seller identity as proof of
  access.

Globally unique stored filenames make one gallery file map to at most one
product.

## 14. Maintenance and file lifecycle

The `maintenance images` command must include both
`Product.image_filename` and `ProductImage.filename` when calculating
references.

It reports:

- missing referenced files;
- orphan normalized JPEGs; and
- cover drift where position 0 and `Product.image_filename` disagree.

Read-only mode never changes files or rows. Existing explicit
`--delete-orphans` behavior deletes only files that are referenced by neither
source and retains its “stop writers first” requirement.

Account anonymization/archive, checkout, Sold status, saving, messaging and AI
training do not delete gallery files. A picture is deleted only after a
successful gallery replacement or an explicit future product-deletion policy.

## 15. Security and privacy

- Login and CSRF remain required for creating/editing listings.
- The seller comes from `current_user`; browser fields cannot choose ownership.
- Every file is independently read with a bounded `5 MiB + 1 byte` check.
- File count and combined size are checked server-side before permanent
  business data commits.
- Client MIME, extension, order and previews are untrusted.
- Original filenames and local filesystem paths are never stored in the
  database or public URLs.
- Only new normalized JPEG bytes are permanently stored.
- UUID filenames, path containment and symlink protections remain.
- Uploaded SVG, HTML, scripts, polyglots, animated files and decompression-bomb
  inputs remain rejected by current byte/image checks.
- Product titles and filename display text remain escaped.
- No image is sent to analytics, a CDN or another third party. Only the cover
  goes to the configured AI provider after the seller sees the disclosure and
  has AI enabled.
- Generic failures never expose SQL, exception text, secret keys or filesystem
  paths.

## 16. Accessibility and responsive design

- The native multiple file control remains labelled, keyboard reachable and
  usable without drag/drop.
- Instructions and limits are programmatically associated with the input.
- Preview and product thumbnail lists use list/figure semantics where helpful.
- Selection status is announced politely; drag-hover alone is not repeatedly
  announced.
- Thumbnail links meet at least a 44 × 44 CSS-pixel activation area.
- Visible focus, selected border and text/current semantics do not depend on
  color alone.
- Long titles/filenames wrap without horizontal page overflow.
- Gallery works at desktop, 320/360-pixel portrait, short landscape and 200%
  zoom when browser controls permit.
- Dark mode and reduced-motion settings retain readable boundaries/focus.
- Main images preserve aspect ratio and do not create layout shifts between
  thumbnail selections beyond the fixed image frame.

## 17. Error behavior and edge cases

The later test plan must cover at least:

- zero, one, two and exactly five images;
- six or more images;
- each file exactly/just over 5 MiB;
- aggregate exactly/just over 25 MiB;
- multipart request over 26 MiB and safe 413 response;
- mixed JPEG/PNG and upper/lowercase extensions;
- empty MIME with supported extension;
- corrupt/spoofed bytes, HTML/SVG, animation and decompression-bomb cases;
- one bad file among four good files, with no partial rows/files;
- landscape, portrait, square and transparent PNG normalization;
- duplicate-looking files and independently generated safe names;
- long/Unicode/HTML-like original filenames shown only as text;
- selection replacement and object-URL cleanup;
- drop versus picker, nested drag events and directory drops;
- browser inability to attach a multiple dropped FileList;
- JavaScript disabled and missing DataTransfer/object-URL APIs;
- AI analysis receives only the first file and stale analysis is cancelled;
- text AI requests receive no images;
- create replay with one product/one gallery;
- create database/storage failure compensation;
- edit with no files (keep), valid full replacement and failed replacement;
- stale simultaneous edit retaining the old gallery;
- existing single-image migration/backfill and legacy fallback;
- cover pointer/position-0 synchronization;
- ordered rendering and keyboard thumbnail selection;
- selected-image/lightbox synchronization;
- one missing gallery file, all missing and unreferenced orphan media;
- active, sold, archived-owner and archived-stranger media authorization;
- cards still show only the cover;
- maintenance missing/orphan/drift reporting; and
- all previous image, listing, lightbox, AI, cart, order and mobile tests.

## 20. Out of scope

MM-026 does not include:

- more than five photos;
- video, GIF animation, SVG, HEIC, WebP or remote image URLs;
- drag-to-reorder, cropping, rotation, filters, annotations or captions;
- deleting one current image or a dedicated Remove All action;
- a lightbox slideshow with Previous/Next arrows;
- server-generated thumbnail files or CDN/object-storage integration;
- background upload progress or saving images before Save Listing;
- AI description generation, best-photo selection or analysis of all five;
- automatic product-image generation;
- copying images into order history; or
- public deployment/storage quota management.

These can be separate specifications because each adds meaningful storage,
privacy, accessibility or lifecycle rules.

## 21. Concepts to understand

### One product, many image rows

This is a **one-to-many relationship**. One Product is like a folder; its
ProductImage rows are numbered photos inside that folder. The `position` number
keeps their order stable.

### The cover is position zero

Cards need one quick picture, not an entire gallery. Position 0 is the cover,
and the older `image_filename` field keeps a matching pointer for existing card
code. It is similar to a book having many pages but one cover.

### All-or-nothing image saving

Suppose photos 1–4 are good but photo 5 is corrupt. Saving only four would
surprise the seller. Market Mirror cleans up all newly created files and saves
none of the gallery. This combines a database transaction with **file
compensation**, because ordinary files are not automatically rolled back by a
database.

### A browser preview is not an upload

`URL.createObjectURL` gives the browser a temporary local address for a chosen
file. The picture is not stored on Market Mirror until the seller submits the
form and the server validates it.

### Progressive enhancement

The multiple file input and thumbnail links work in a basic form without
JavaScript. JavaScript adds convenient previews and in-page switching. This is
called progressive enhancement: the useful foundation still works when the
enhancement is unavailable.
